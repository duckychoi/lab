# spec-kit: Toolkit to help you get started with Spec-Driven Development

**GitHub**: https://github.com/github/spec-kit
**지표(2026-09-06 API 실측)**: ⭐ **133,645** · fork **12,026** · 오픈이슈 **316** · Python · **MIT** · 생성 2025-08-21 · push 2026-09-04
**raw 수집값(09-05)**: ⭐133,541 → **+104**. 절대값만 채택.

> [!insight] 핵심 인사이트 — **프로세스를 도구가 "강제"한다는 것이 이 레포의 주장이다**
> SDD(Spec-Driven Development)의 요지는 단순하다: **에이전트에게 코드를 시키기 전에 명세를 확정시킨다.** 새로운 건 아이디어가 아니라 **강제 수단**이다 — 이 레포는 그것을 문서 권고가 아니라 **CLI 절차**로 만든다.
> 여기서 볼트가 이미 가진 반대 명제와 정면으로 만난다. [[mattpocock-skills]]의 문제 제기가 정확히 *"GSD·BMAD·**Spec-Kit**이 개발 프로세스 전체를 소유해 버려 프로세스 자체의 버그를 잡기 어렵다"* 였다. **이 배치는 그 논쟁의 양쪽을 같이 들여왔다.**

> [!insight] 오픈이슈 316건 — 배치 내 최저 마찰
> **issue/star = 0.0024.** [[opencode]](0.0278)의 **1/12**, [[hermes-agent]](0.160)의 **1/67**이다. 같은 배치에서 이 격차는 우연으로 보기 어렵다.
> 해석 두 가지가 가능하고 **둘을 구분할 근거가 없다**: (a) GitHub 공식 조직이라 이슈 관리가 촘촘하다, (b) 도구 표면적이 작아 실제로 덜 깨진다. ⚠️ **낮은 이슈 밀도를 품질 근거로 바로 읽지 않는다** — 관리 강도와 결함 밀도가 같은 숫자에 섞여 있다.

> [!warning] ⚠️ "특정 에이전트 비종속"은 주장이며 검증되지 않았다
> 레포는 any AI coding agent 대상임을 표방한다. 그러나 **어느 에이전트에서 어느 정도로 동작하는지에 대한 대조표가 없다.** [[Repo-To-Skill]]이 세운 기준(**백본·하네스·예산 고정 후 변수 하나만 토글**)을 이 레포는 충족하지 않는다 — 프로세스 도구 층 전반의 공백이다.

## 도메인별 추출 (ai-news)

- **신뢰도**: ⭐⭐⭐⭐ high — API 실측. **GitHub 공식 조직(id 9919)** 이라는 출처 자체가 강한 신호.
- **즉시 활용**: **YES.** Python + MIT, 설치 마찰 낮음. 볼트의 [[Claude-Code-워크플로우]]에 **명세 선행 단계**를 붙이는 실험이 바로 가능하다.
- **6개월 영향력**: **높음.** 빅테크 공식 조직이 *"에이전트에게 시키기 전에 명세를 굳혀라"* 를 CLI로 못박았다는 사실 자체가 업계 기본값을 민다.
- **대체 관계**: [[mattpocock-skills]]와 **정면 대립**. 전자는 *프로세스를 잘게 쪼개 수정 가능하게*, 이쪽은 *프로세스를 통째로 규정해 이탈을 막는다*. **어느 쪽이 옳은지 판정할 정량 근거가 양쪽 다 없다** — 이 대립 자체를 [[에이전트-스킬]]에 축으로 기록한다.
- **허와 실**: 실은 **공식성·낮은 이슈 밀도·활발한 push**. 허는 **"명세 우선이 결과를 개선한다"는 명제의 무근거성**.
- **액션**: 볼트 자체 실험 — 동일 과제를 (a) 바로 지시 (b) spec-kit 명세 선행 두 조건으로 돌려 **차이를 관측**(중간). 이것이 이 레포에 대한 유일하게 정직한 판정 방법이다.

> [!question] 미해결 질문
> - **명세가 틀렸을 때 비용은?** 프로세스를 굳히는 도구는 **잘못된 명세도 같이 굳힌다.** [[mattpocock-skills]]의 비판이 정확히 이 지점이며, 레포 문서에 이탈·수정 절차가 있는지 미확인.
