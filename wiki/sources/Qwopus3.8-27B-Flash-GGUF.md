# Qwopus3.8-27B-Flash-GGUF

> [!insight] 핵심 인사이트
> Qwen3.8-27B 파인튜닝인데 목표가 특이하다 — **능력 향상이 아니라 추론 비용·지연 절감**이다.
> 근거로 카드가 제시하는 논리: **에이전트 루프가 모델 호출을 수십~수백 회로 증폭**한다. 턴당 5초가 추가되면 **50턴 과제에 250초**가 붙는다.
> → **에이전트 시대에는 "조금 더 똑똑한 모델"보다 "조금 더 빠른 모델"이 이길 수 있다**는 주장. 벤치마크 점수 경쟁과 다른 축을 명시적으로 택했다.

> [!note] 📊 얻은 것 (카드 원문 실측)
> 3과목(수학·물리·화학) 총계 기준:
> - **디코딩 9.347 tok/s vs 베이스 8.284 (+12.8%)**
> - **MTP 드래프트 수용률 80.7% vs 66.1% (+14.6pp)** — 과목별 +14.5~14.8pp로 **균일**
> - `raw_output` 총 문자수 **7,949,546 vs 8,824,213 (−9.9%)** = **폭주 추론 감소**(수학 −17.7% · 물리 −8.8% · 화학 −5.8%)
> → 수용률 상승이 과목 무관하게 균일한 것이 신뢰 요소. **특정 과목에 과적합된 게 아니다.**

> [!warning] 📊 잃은 것 — 카드가 직접 명시 (볼트 원문 대조)
> - **MMLU-Pro 혼합 2,500문항 91.28% vs 베이스 92.73% → −1.45pp**
> - 카드 본문 원문(78행·181행): *"추론 효율을 개선하는 대신 **MMLU-Pro 점수가 낮아지는 명시적 트레이드오프**"* · *"아래 디코더 전용 처리량 결과는 **속도를 측정한 것이지 정답 정확도가 아니다**"*
> → 🎯 **트레이드오프를 카드가 먼저 말한다.** 이 배치 [[Qwen3.8-Flash-Next-NVFP4]] 가 표 서식으로 수치를 가린 것과 **정반대의 정직함**.

> [!warning] 비교 주장으로 쓸 수 없는 수치 2건
> - 에이전트 SWE 배터리 **13/14(93%)**, RTX 5090 1장에서 26.0분 — 그러나 표의 **베이스 비교값이 `—`(없음)** 이고 *"엄격한 단일 실행"* 이므로 **비교 주장 불가**
> - "end-to-end 처리량 ~8% 향상" — 카드 자체가 *"별개의 근사 측정"* 이라 표기
> → **카드가 자기 수치의 등급을 구분해 표시한다.** 인용할 때 이 구분을 지워버리면 안 된다.

> [!warning] 🔴 raw가 누락한 것 — 이 모델은 멀티모달이다
> raw는 이 모델을 **텍스트 추론 모델로만** 기술했다. 볼트 실측 결과 그렇지 않다:
> - HF API 태그: **`vision` · `multimodal` · `image-text-to-text`**
> - 카드 프론트매터 39행: **`pipeline_tag: image-text-to-text`**
> → **비전 입력을 받는 모델**이다. raw는 벤치마크(수학·물리·화학·MMLU-Pro)가 전부 텍스트라 **텍스트 모델로 추론**했다.
> → 09-09 규칙 *"이름에서 기능을 추론하지 말 것"* 의 **변형**: **"벤치마크 구성에서 입력 모달리티를 추론하지 말 것."** 평가가 텍스트만 다뤘다고 모델이 텍스트 전용인 건 아니다.

> [!warning] 알려진 결함 자인
> **일부 Python 과제에서 잘못된 들여쓰기 코드 생성** — 수정 진행 중.
> → 파이썬 들여쓰기는 문법 오류로 직결된다. **코딩 용도라면 이 항목이 치명적**일 수 있다.

## 도메인별 추출 (local-llm)

- **실용성 판단**: **매우 높음.** 다운로드 **113,295**(♥176, **비율 644:1**) — **이 배치 3개 모델 중 압도적 1위**이며 [[MiniCPM5-2B]](2.9:1)와 극단적 대비. GGUF/llama.cpp라 **바로 돌아간다**는 점이 실사용 비율로 나타났다. **커뮤니티 검증이 실제로 존재하는 유일한 항목.**
- **메모리 아키텍처**: GGUF **Q5_K_M + MTP** 구성으로 측정. **MTP(Multi-Token Prediction) 드래프트 수용률**이 핵심 지표 — 투기적 디코딩의 효율이 곧 속도다.
- **Hermes 적용**: **가장 현실적인 후보.** 이유는 성능이 아니라 **에이전트 루프 특성** — 내 워크플로우도 호출을 수십 회 증폭시키므로 **턴당 지연 절감이 누적 효과**를 낸다. −1.45pp 지식 손실은 **툴을 쓰는 에이전트에겐 대체로 감당 가능**.
- **트레이드오프**: **명시적이고 정량적이다** — 속도 +12.8% / 수용률 +14.6pp / 출력량 −9.9% ↔ MMLU-Pro **−1.45pp**. 이 배치에서 **트레이드오프를 가장 정직하게 공개한 항목**.
- **오픈소스 구현체**: **Apache-2.0** · base `Qwen/Qwen3.8-27B` · llama.cpp·Ollama·LM Studio 즉시 사용 · unsloth 계열 태그.

> [!action] 당장 할 것
> **Ollama로 받아 내 에이전트 루프에 그대로 물려 A/B**: 베이스 대비 **총 소요시간**을 잰다. 카드가 준 건 tok/s인데 내가 알아야 할 건 **과제 완료까지의 벽시계 시간**이다. 단 **①Python 들여쓰기 결함 ②비전 입력 지원** 두 가지를 실측으로 확인할 것.

> [!question] 미해결 질문
> 벤치마크가 전부 텍스트(수학·물리·화학·MMLU-Pro)인데 **비전 성능은 카드에 측정이 없다**. 파인튜닝이 비전 쪽 능력을 훼손했는지 **알 수 없다** — 멀티모달 용도라면 반드시 자체 확인 필요.
