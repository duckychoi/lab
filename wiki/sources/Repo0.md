# Repo0 — 레포 아키텍처를 "가정"하지 않고 진화시켜 짓는다

**논문**: https://huggingface.co/papers/2608.19854 (arXiv 2608.19854)
**지표**: HF 데일리 **9위** · 업보트 **16** · 게재 2026-08-20 · 저자 8인(Silin Chen·Haoyi Teng·Xiaodong Gu 외)
**검증**: 2026-08-22 HF API 실호출 — 제목·초록·업보트·저자 **원문 대조 완료**

> [!insight] 핵심 인사이트 — 기존 코드 에이전트의 숨은 전제는 "레포 구조는 이미 정해져 있다"
> LLM 에이전트의 코드 생성은 크게 발전했지만, 대부분의 시스템은 **미리 정의된 레포지토리 아키텍처를 가정**한다. 이 가정은 **zero-to-all 코드 생성**(자연어 요구사항만으로 프로젝트 전체를 짓되 개발 내내 모듈러 아키텍처를 유지)에서는 성립하지 않는다.
>
> Repo0는 아키텍처 상태를 **Dual-DAG**로 명시적으로 인스턴스화한다 — **요구사항 수준 DAG** + **컴포넌트 수준 DAG** + **둘의 정렬 관계**. 자연어 요구사항에서 출발해 **모듈성 지표(modularity metrics)가 유도하는 구조적 액션**으로 컴포넌트 경계를 반복 진화시키고, **구조 수렴** 후에야 수렴된 아키텍처가 **TDD 코드 생성**을 이끈다.
>
> **정량 결과**: RepoCraft의 실세계 레포 6개에서 GPT-5 mini·DeepSeek V3.2로 평가. 모든 설정에서 Functionality Coverage·Pass Rate 최고. 최강 레포 계획 베이스라인 **RPG 대비 Functionality Coverage 최대 +20.08%p, Pass Rate 최대 +29.74%p**. 어블레이션으로 Dual-DAG 상태·모듈성 유도 구조 진화·명시적 구조 수렴 각각의 기여를 확인.

> [!note] "계획 후 코딩"의 계보에서 Repo0의 위치
> [[superpowers]]가 *프로세스* 차원에서 "코드부터 짜지 말고 스펙→계획→서브에이전트 실행"을 강제한다면, Repo0는 그 계획을 **기계가 읽고 최적화할 수 있는 자료구조(Dual-DAG)** 로 못박고 모듈성 지표로 수렴 판정을 자동화한다. 즉 같은 신념의 **프롬프트 규율판 vs 알고리즘판**.

## 도메인별 추출 (ai-news / 교차: agent-eval · 코드 에이전트)

- **신뢰도**: ⭐⭐⭐⭐ — HF 데일리 9위·업16. **초록·수치·베이스라인·평가 모델 원문 실검증 완료**(raw 메모의 "통과율 수치 미확인"은 실제로는 **확인됨** — Pass Rate +29.74%p).
- **즉시 활용**: **부분 YES(개념)** — 코드 없이도 **"요구사항 DAG ↔ 컴포넌트 DAG를 따로 유지하고 정렬을 명시한다"**는 설계는 [[Claude-Code-워크플로우]]에서 신규 프로젝트 스캐폴딩 시 수동 모사 가능(요구사항 목록과 모듈 목록을 별도 문서로 두고 매핑표 유지).
- **6개월 영향력**: 중간~높음 — "에이전트가 파일 하나를 고친다"에서 **"에이전트가 프로젝트 구조를 소유한다"**로 범위가 넓어지는 흐름. [[SWE-bench-Science]]·[[SWE-bench]] 계열이 *기존 레포 수정* 능력을 재는 것과 대비해, Repo0는 *무에서 구조 짓기*를 겨냥.
- **대체 관계**: [[superpowers]] 방법론과 상보(프로세스↔자료구조). RPG 등 레포 계획 베이스라인을 직접 대체 주장.
- **허와 실**: 6개 레포는 **작은 표본**이고 RepoCraft 벤치의 난이도 분포가 결과를 좌우할 수 있다. "모듈성 지표"가 무엇인지 초록 미기재 — 지표를 최적화 목표로 삼으면 **지표 해킹**(모듈성 점수는 좋지만 실사용 나쁜 구조) 위험이 상존. 평가에 GPT-5 mini·DeepSeek V3.2를 썼다는 점도 대형 모델에서의 이득 지속 여부를 미확정으로 남긴다.
- **액션**: 개념 참조 — 다음 신규 프로젝트에서 요구사항↔컴포넌트 매핑표를 명시 유지하는 실험 1회.
