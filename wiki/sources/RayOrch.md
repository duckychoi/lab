# RayOrch (arXiv/HF 2609.18703)

**정식 제목**: *RayOrch: Programming and Executing Lineage-Controlled Multi-Grain Dataflows for Foundation-Model Data Preparation*

> [!insight] 핵심 인사이트 — **부모-자식 관계를 잃지 않는 것이 성능 문제였다**
> 파운데이션 모델 학습데이터 전처리는 **입도(granularity)가 계속 바뀐다** — 문서→페이지, 영상→클립. 자식을 부모 경계 너머 GPU에 흩뿌리면 빨라지지만 **순서·완료상태·결과 라우팅을 잃는다.**
> RayOrch 는 **부모-자식 계보를 실행 전 구간에서 보존하는 프로그래밍 모델 + 분산 엔진**이다. 계보를 유지하면서도 자식을 자유롭게 배치한다.
> 🎯 **오늘 논문 5건 중 유일하게 "경쟁 시스템 실명 + 상대 개선율" 을 둘 다 제시한다** — Ray Data · Daft · Docling 을 이름으로 부른다.

## 정량 수치 (초록 기준)

**축 A — 자기 대비 스케일링 (H20 GPU)**

| 파이프라인 | 확장 | 배수 |
|---|---|---|
| MinerU | 4 → 64 GPU | **15.14배** |
| 영상 파이프라인 | 8 → 64 GPU | **7.82배** |

**축 B — 경쟁 대비 종단시간 단축**

| 워크로드 | 대조군 | 개선 |
|---|---|---|
| MinerU | Ray Data | **−13.1%** |
| MinerU | Daft | **−29.0%** |
| Docling | Ray Data | **−16.0%** |

> [!warning] 📌 두 축을 같은 칸에 넣지 마라 — 수집기 경고가 옳다
> **15.14배는 자기 대비 스케일링**(GPU 16배 늘렸을 때의 처리량)이고, **−13.1%는 경쟁 대비 종단시간**이다. **완전히 다른 축이다.**
> 🎯 실제로 이 둘은 **반대 방향으로 읽힌다**: 15.14배는 *"RayOrch 는 잘 확장된다"*, −13.1%는 *"RayOrch 는 Ray Data 보다 조금 빠르다"*. **전자가 인상적이고 후자는 겸손한데, 사용자에게 의미 있는 건 후자다.** 15.14/16 = **94.6% 스케일링 효율**로 환산하면 인상이 정확해진다.
> ⬜ **볼트 미확인**: 4 GPU 시점의 절대 처리량이 초록에 없다. 스케일링 효율은 계산되지만 **출발점 성능은 모른다** — 느린 출발에서 잘 확장되는 것과 빠른 출발에서 잘 확장되는 것은 다르다.
