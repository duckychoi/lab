# Qwen-Planner-Agent

> [!insight] 🎯 핵심 인사이트 — **"모델–하니스 공진화"가 볼트가 추적해 온 축의 정면 진술이다**
> 데이터 생산·모델 학습·배포를 **공유된 action-feedback-verification 계약**으로 연결한 AI-for-AI 폐루프. 세 축:
> - **(i) AI for Data** — 사람이 게이트를 잡는 agentic 데이터 플라이휠. 전문 에이전트들이 과제를 만들고 trajectory 를 모으고 학습 데이터를 큐레이션·균형화하며, 🎯 **학습 피드백이 다음 데이터 생성을 지시**한다(단방향 파이프라인이 아님).
> - **(ii) AI for Training** — 지도 플래닝 콜드스타트 + 하이브리드 환경 온라인 agentic RL + **CARE**(Competence-Aware Reward-and-Advantage Engineering)로 추론·도구사용 **비용을 줄이면서** 성능 유지.
> - **(iii) 모델–하니스 공진화** — 런타임에 **메모리·스킬·도구를 오케스트레이션**하고, 구조화된 행동 피드백과 🎯 **보존된 실패 trace** 를 **모델과 하니스 양쪽** 적응에 되먹인다.
> 📌 **(iii)이 볼트에 직접 값을 낸다.** 볼트는 [[하네스-설계-축]]·[[하네스형-에이전틱-RL]]에서 *"성능이 모델에서 오는가 하니스에서 오는가"* 를 반복 물었다. 이 논문은 **그 질문을 학습 루프의 구조로 만든다** — 둘을 분리해 귀속하려 하지 않고 **함께 갱신되는 쌍으로 취급**한다.
> 🎯 그리고 **"보존된 실패 trace"** 가 [[검사가능성-공사]] 와 만난다: 실패를 버리지 않고 **자산으로 유지**한다는 것은 *"확인되지 않음/실패" 상태를 일급 객체로 둔다*는 뜻이다.

> [!note] 문제 선택 근거 — 왜 모바일 플래닝인가
> 두 가지를 든다: ① 모바일 플래닝이 **long-horizon 신뢰성**을 요구한다 ② 🎯 **실기기 상호작용 비용이 개발 확장성을 제약한다.**
> ②가 솔직하고 구조적이다 — 실기기는 느리고 병렬화가 어렵고 상태가 더럽다. 그래서 하이브리드 환경(시뮬 + 실기기)이 설계에 들어간다.
> 📌 같은 배치 [[mobile-mcp]] 와 **같은 병목을 다른 층에서 다룬다**: mobile-mcp 는 *"접근성 트리로 관측 비용을 줄인다"*(도구층), 이 논문은 *"하이브리드 환경으로 학습 비용을 줄인다"*(학습층). **모바일 에이전트의 비용 문제가 두 층에서 동시에 공격받고 있다.**

> [!warning] 🔴 초록에 구체 점수·베이스 모델명·경쟁 모델명이 하나도 없다
> 성능 주장: **MobilePA-Bench 에서 평가 대상 전 모델·시스템 중 최고 종합 성능**. 베이스 모델 대비 **도구사용·메모리·스킬·서브에이전트 조율** 항목 개선. 비모바일 agentic 벤치마크에서도 개선하면서 일반 능력은 *"largely preserving"*.
> 🔴 **"best overall" 은 자기보고이고 대조군이 공개되지 않았다.** ✅ 수집기가 *"점수·베이스명·경쟁명 0개"* 를 밝히고 *"largely preserving"* 을 **"전부 보존이 아님"** 으로 한정어를 살린 것은 정확하다(볼트 재확인 일치).
> 🎯 **그리고 MobilePA-Bench 가 자사 명칭 가능성이 있다** — 이름 구조가 `Mobile` + `PA`(Planner Agent?)로 이 논문의 대상과 정확히 맞는다. ⬜ **제3자 벤치인지 자사 벤치인지 확인하지 않았다.** 자사 벤치에서 자사 모델이 1위인 것은 [[분포내-우위]] 문제다. **확인 전에는 단정하지 않는다.**
> 🔴 부속 GitHub **`None`**(볼트 재확인 일치) — **"AI가 AI를 만드는 폐루프"를 주장하면서 코드 링크가 HF 메타데이터에 없다.**

## 도메인별 추출 (local-llm)

> [!note] 🔀 도메인 재판정 — raw `ai-news` → **`local-llm`**
> 근거: local-llm 도메인 정의가 *"Local/Edge/Small LLM + **에이전트 메모리**"* 이고, 이 논문의 (iii)이 **런타임 메모리·스킬 오케스트레이션**을 정면으로 다룬다. 또한 모바일 = 온디바이스 제약 환경이다. `ai-news` 로 두면 메모리 아키텍처 축의 누적에서 빠진다.

- **실용성 판단**: 🔴 **학습은 불가, 구조는 가능.** 폐루프 전체는 데이터·컴퓨트·실기기 팜을 요구한다. ⬜ 모델 공개 여부·파라미터 규모 **초록에 없음** — 배포 가능성 판단 근거가 없다.
- **메모리 아키텍처**: 🟡 **"메모리·스킬·도구 오케스트레이션"이라고만 적혀 있다.** RAG/KV/압축/외부DB 중 무엇인지 **초록에 없다.** 🎯 다만 **"보존된 실패 trace"** 는 구체적 단서다 — 성공 궤적만 저장하는 통상 방식과 달리 **실패를 인덱싱**한다는 뜻이고, 이는 [[에이전트-메모리-레이어]] 설계 선택으로 의미가 있다.
- **Hermes 적용**: 🟡 **원칙 2개는 지금 적용 가능하다** — ① **실패 trace 보존**(성공만 남기지 않기) ② **피드백이 다음 입력 생성을 지시**하는 역방향 연결. 둘 다 코드가 아니라 설계 규약이라 규모 무관. 🔴 CARE 는 RL 학습 기법이므로 적용 불가.
- **트레이드오프**: 🔴 **수치가 0개라 트레이드오프를 말할 수 없다.** CARE 가 *"비용을 줄이면서 성능 유지"* 라 주장하는데 **줄인 비용도 유지한 성능도 숫자가 없다.**
- **오픈소스 구현체**: 🔴 **없다**(부속 GitHub 부재). 이름에 `Qwen` 이 있어 [[Alibaba]] 계열로 추정되나 **초록·메타데이터로 소속을 확정하지 못했다** — 저자 26명 규모는 기업 팀과 정합하지만 추정이다.
