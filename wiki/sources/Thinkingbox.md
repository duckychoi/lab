# Thinkingbox — 에이전트 평가의 기준을 "성공률"에서 "재현성"으로 옮긴다

**논문**: https://huggingface.co/papers/2608.19741 (arXiv 2608.19741)
**원제**: *One Success Isn't Reliability: Thinkingbox, a Sandbox and Benchmark for Agents in Stateful Business Workflows*
**지표**: HF 데일리 **5위** · 업보트 **6** · 게재 **2026-08-20** · 저자 **12인**
**코드**: https://github.com/microsoft/thinkingbox ([[Microsoft]] · 샌드박스와 벤치 **둘 다 공개**)
**검증**: 2026-08-25 HF API 실호출 — 제목·초록·수치·업보트·저자수·코드 링크 **원문 대조 완료**

> [!insight] 핵심 인사이트 — 이번 배치에서 가장 중요한 숫자 두 개
> **최강 모델이 pass@1 65.36%인데 pass^20은 25.25%.**
>
> pass@1은 "20번 중 한 번이라도 성공"에 가까운 관대한 지표이고, **pass^20은 "20번 모두 성공"** 을 요구한다. 같은 태스크 집합에서 이 둘이 **65% → 25%로 벌어진다**는 것은, 우리가 흔히 인용하는 에이전트 성능 수치가 **업무 위임 가능성과 거의 무관하다**는 뜻이다. 실무에서 필요한 건 "가끔 되는" 에이전트가 아니라 "매번 되는" 에이전트다.
>
> 제목이 곧 논지다 — **One Success Isn't Reliability.**

> [!insight] 더 불편한 발견 — 툴콜 신호가 완수의 대리 지표가 아니다
> **실패한 시도들 상당수가 "깨끗한 종료(clean termination)"와 "유효한 상태 변경 액션"을 보여줬다.** 즉 로그만 보면 잘 돌아간 것처럼 보이는데 실제로는 태스크를 완수하지 못했다.
>
> 함의가 크다: **응답 수준·툴콜 수준 신호로 에이전트 성공을 모니터링하는 관행이 구조적으로 실패한다**는 실증이다. "에러 없이 끝났으니 됐다"는 판단이 통하지 않는 영역이 있다는 것 — 프로덕션 에이전트 관측성(observability) 설계에 직접 타격.

> [!note] 샌드박스 설계 — MCP 호환·전체 트레이스·최종 상태 채점
> 세 요소로 구성된다: **격리된 MCP 호환 툴 세션** + **완전한 실행 트레이스** + **터미널 백엔드 상태 기반 결과 평가**.
>
> **Thinkingbox-bench**는 **507개 정책 조건부(policy-conditioned) 워크플로**로, 도메인은 **리테일 · 호텔(hospitality) · 자동차보험 · 네오뱅크 내부 IT · 컨설팅 IT/HR 지원** 등이다. 채점은 **태스크별 실행 가능 체크**로 이뤄지는데 — **유효한 궤적은 받아들이되, 틀렸거나 누락됐거나 "여분의(extra)" 효과는 거부**한다. 부수효과(collateral effect)까지 감점한다는 뜻으로, 실무 요구에 부합한다. 지정된 태스크는 **최종 응답의 요구 속성**까지 추가 검사한다.

> [!action] 당장 할 것 — 내 워크플로에도 pass^k를 적용한다
> 이 논문의 방법론은 코드 없이도 즉시 이식된다. 자동화에 맡기는 작업을 **한 번 성공했다고 채택하지 말고, 같은 입력으로 5~10회 반복해 전부 성공하는지 확인**한다. [[Claude-Code-워크플로우]]나 스케줄 자동화처럼 **반복 실행되는 파이프라인일수록 pass^k가 진짜 지표**다. 특히 "에러 없이 끝남"을 성공 판정으로 쓰고 있다면 **최종 상태를 직접 확인하는 체크로 교체**해야 한다.

## 도메인별 추출 (ai-news / 교차: agent-eval · 엔터프라이즈 에이전트)

- **신뢰도**: ⭐⭐⭐⭐⭐ — **이번 배치 최고**. 초록 원문 실검증 완료이며 **정량 수치(65.36/25.25)·규모(507)·도메인 목록·채점 방식이 모두 명시**되고 **코드까지 공개**됐다. 배치 내 다른 논문들이 "수치 미기재"인 것과 뚜렷이 대비.
- **즉시 활용**: **YES** — (1) pass^k 관점을 자체 자동화 검증에 즉시 적용, (2) MCP 호환 샌드박스이므로 **내 MCP 툴 세팅을 그대로 얹어 평가** 가능, (3) "부수효과 감점" 채점 철학을 자체 체크 설계에 차용.
- **6개월 영향력**: **높음** — pass^k가 에이전트 논문의 표준 보고 항목으로 굳으면 **기존 성능 주장 상당수가 재평가**된다. [[Microsoft]]가 샌드박스+벤치를 함께 공개했다는 점에서 채택 장벽도 낮다.
- **대체 관계**: [[MobilePA-Bench]]와 **같은 배치·같은 문제의식**(상태 기반 채점)이나 **수치 구체성에서 이쪽이 압도적**. [[EnterpriseClawBench]]·[[MerchantBench]]와 엔터프라이즈 축에서 인접, [[MemTrapBench]]와는 "기존 성능 서사를 깨는 벤치" 계보.
- **허와 실**: **최강 모델이 무엇인지 초록에 없다** — 65.36%가 어느 모델의 수치인지 모른다. 507개 워크플로의 난이도 분포도 미기재라, pass^20 25.25%가 **태스크가 어려워서인지 에이전트가 불안정해서인지** 초록만으로는 분리되지 않는다. 또 pass^20은 **정의상 매우 가혹한 지표**여서, 이 격차의 일부는 지표 선택 효과일 수 있다는 점을 감안해야 한다(그럼에도 격차의 크기 자체는 유의미).
- **액션**: github.com/microsoft/thinkingbox 확인 — **507 워크플로의 채점 스크립트 구조**를 자체 검증 체크 작성 시 템플릿으로.

> pass@1 65.36%를 낸 "최강 모델"은 무엇인가? 오픈웨이트 모델들의 점수는? 507개의 난이도 분포는? pass^20의 실패가 특정 도메인에 몰리는가? MCP 호환의 범위는 어디까지인가?
