# univer — AI 에이전트용 오피스 런타임

> [!insight] 핵심 인사이트 — **이 항목의 발견은 기술이 아니라 타이밍이다**
> 스프레드시트·문서·슬라이드·Bases·보드를 **한 런타임 + 하나의 Facade API** 로 제공하는 임베더블 오피스 SDK. 플러그인 아키텍처 · Canvas 렌더링 · 수식 엔진 · 브라우저/Node.js 양쪽 동작. PDF는 *coming soon*.
> 🎯 그런데 **생성일이 2022-09-29 — 4년 된 레포다.** 그게 지금 *"The Office Harness for AI Agents"* 로 불린다.
> 📌 **코드가 새 것이 아니라 포지션이 새 것이다.** 에이전트 붐이 기존 SDK에 새 이름을 붙여 주는 현상의 선명한 표본. [[하네스-설계-축]] 에 *"하네스는 새로 만들어지기도 하지만 **개명되기도 한다**"* 는 칸이 필요하다.

> [!question] ⬜ 리포지셔닝인가, 실제 기능 추가인가 — **가르지 못했다**
> 에이전트가 이 SDK를 쓰려면 **툴 호출 인터페이스·구조화된 상태 노출·결정적 편집 API** 가 있어야 한다. Facade API가 그 역할을 하는지, 아니면 기존 프론트엔드 API를 에이전트용이라 부르는 것뿐인지가 이 항목의 핵심 질문이다.
> 🔴 **볼트 확인 범위: README 상단 ~2.6KB만 — 405행 전문 미열람.** 따라서 *"에이전트 전용 기능이 없다"* 고 말할 수 **없다.** 모른다.
> → 다음 배치 확인 항목: README 전문 + `Facade API` 문서에서 **툴 스키마/MCP 연동 유무**.

> [!note] 왜 오피스 포맷이 에이전트 하네스로 거론되는가
> 에이전트 산출물의 상당수가 **표·문서·슬라이드**다. 그런데 LLM이 파일 포맷을 직접 쓰면 [[포맷-불일치-오염]] 이 난다. **런타임을 끼우면 편집이 구조화된 연산이 되고 검증 가능해진다** → [[스키마-준수-보장]] 과 같은 논리.
> 🔀 볼트 인접 사례: [[docling]](문서 → 구조화 파싱, 입력 방향) ↔ univer(구조화 → 문서, **출력 방향**). 같은 문제의 반대편.
