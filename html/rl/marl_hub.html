📖 해석 Q&A — 알고리즘 역할·조합·구현 위치

아래는 각 카드의 코드 대조 결과를 바탕으로, 실제 구현자가 네트워크를 바꿀지, PPO/QMIX loss를 바꿀지, 러너·버퍼까지 바꿔야 하는지 바로 판단하도록 정리한 해석이다. 기준일: 2026-06-17.

1. Sable은 MARL용 트랜스포머인가?

결론: Sable은 MARL용 Transformer-like 시퀀스 백본으로 보는 게 맞다. 다만 표준 self-attention 대신 MultiScaleRetention을 쓰는 RetNet 계열이다. 카드 02의 코드 근거처럼 encoder/decoder 구조, causal decode, agent/time positional encoding, value head가 있어 MAT류 autoregressive MARL 정책망 역할을 한다.

장점: 긴 시퀀스(시간×에이전트)를 attention보다 효율적으로 처리하고, 학습 때는 전체 시퀀스를 병렬/청크로 보고 실행 때는 recurrent 모드로 숨은 상태만 넘길 수 있다. many-agent 또는 long-horizon CTDE에서 중앙집중 표현 + 실행 효율을 동시에 노릴 때 맞다.

2. MAGPO의 Guided Policy Optimization은 PPO를 대체하는가?

부분 대체다. MAGPO는 PPO 생태계의 rollout, GAE, clipped value loss, entropy, minibatch update를 유지하면서, 학습 단계에 guider policy와 guided objective를 추가한다. 즉 "PPO 러너 전체 교체"라기보다 PPO actor update를 guided actor-critic update로 확장하는 쪽에 가깝다.

구성MAGPO에서 바뀌는 점구현 위치
네트워크Sable guider + 분산 RecurrentActor 2개 정책policy/model registry
lossguider는 double-clipped GPO + KL, actor는 PPO 보조손실 + guider KL 정렬learner/update step
데이터동일 rollout을 guider/actor가 공유하되 guider는 전체 agent 시퀀스를 본다batch reshape, CTDE input

3. Sequential Value(SrSv)는 언제 쓰면 좋은가?

SrSv는 행동 순서가 의미 있는 협력에 맞다. 예: 문 통과에서 앞 로봇이 공간을 열고 뒤 로봇이 밀기, 박스 운반에서 선두/후미 역할이 갈리는 경우, 전술 게임처럼 앞 agent 행동이 뒤 agent 선택을 강하게 제약하는 경우다.

구현상 SrSv는 단순히 Transformer actor만 넣는 것이 아니라, decoder attention으로 local value를 재분배해 seq_v = att @ loc_v 형태의 순차 가치 critic을 만든다. 그래서 team reward는 하나인데 "누가 먼저 어떤 기여를 했는가"가 애매한 문제에서 credit assignment 보강용으로 쓴다.

경쟁군서로 비교할 후보핵심 차이

5. S2Q는 PPO나 loss만 대체하는가? MAGPO와 같이 쓸 수 있나?

S2Q는 PPO 대체가 아니다. S2Q는 QMIX/WQMIX 계열의 value-based learner + mixer + multi-Q head 구조다. 따라서 PPO의 policy-gradient loss 한 줄만 바꾸는 방식으로 붙지 않는다. PyMARL류 runner, replay buffer, TD target, mixer 구조까지 포함한 알고리즘 축이다.

S2Q + AIR는 자연스럽다. 둘 다 PyMARL/QMIX 계열이라 S2Q의 다중 Q 표현과 AIR의 individual-recognition auxiliary를 같은 learner 안에 넣는 식이 가능하다. 반면 S2Q + MAGPO는 직접 결합 비용이 크다. MAGPO는 on-policy PPO/JAX/Mava, S2Q는 off-policy value-based/PyMARL라 프레임워크와 학습 신호가 다르다. 실용적으로는 "MAGPO의 guider 철학을 QMIX 계열에 teacher-Q로 이식"하거나 "S2Q의 alternative Q-head 아이디어를 PPO critic ensemble로 재해석"하는 수준이 맞다.

6. Offline RL과 Online RL의 장단점, 사족보행·파쿠르 선택

방식장점단점유리한 태스크
Offline RL실로봇 안전, 비싼 rollout 절감, 사람/기존 정책 로그 활용, 위험 행동 억제dataset 밖 행동에 취약, Q overestimation, 데이터 품질 의존, 새 지형 적응 한계실로봇 로그 기반 fine-tune, 안전 제약, manipulation/locomotion demos
Online RL환경 피드백으로 성능 한계가 높고 curriculum/domain randomization과 잘 맞음시뮬레이터 비용, 실로봇 위험, reward hacking, 탐험 실패 가능Isaac Gym/Lab 대량 병렬 학습, parkour, agile locomotion
Offline-to-online데이터로 warm start 후 online으로 성능·적응성 확보두 파이프라인을 모두 관리해야 함사족보행·파쿠르의 현실적 최선: teacher를 online으로 강하게 만들고, student/RMA/flow policy를 offline 또는 offline-to-online으로 보강

사족보행 파쿠르는 시뮬레이션 online teacher + teacher-student distillation + RMA가 기본축이다. 실로봇 로그가 충분히 쌓이면 offline/flow matching을 safety-aware fine-tune이나 multimodal action prior로 붙이는 편이 낫다.

7. AIR는 loss만 갈아끼우면 구현되는가?

아니다. AIR는 AIR loss 항만 추가하는 게 아니라, individual recognition auxiliary head, adaptive alpha, 별도 optimizer/alpha loss, 기존 QMIX/VDN/QTRAN learner와의 연결이 필요하다. 따라서 "loss 교체"가 아니라 탐험·표현 보조 모듈 추가로 봐야 한다.

8. Teacher-student + RMA와 잘 융화되는 조합

조합어디에 붙나구현 판단
SMPE + RMAstudent/estimator 입력 앞 belief encoder가장 직접적. priv_latent(질량·마찰·COM)를 VAE/belief로 복원하고 student에 증류한다.

9. Diffusion/Flow Matching + RL 후보

2026-06-17 기준으로 실제 코드까지 바로 볼 후보는 FQL이 가장 명확하다. FQL 논문/프로젝트는 flow matching을 action space policy로 쓰며, iterative flow는 BC로 학습하고 one-step policy를 Q값으로 학습해 recursive backprop 문제와 inference latency를 줄인다. 공식 코드는 seohongpark/fql, 프로젝트 페이지는 seohong.me/projects/fql이다.

후보상태핵심 아이디어로봇 적용 판단
FQL / Flow Q-Learning논문 + 공식 코드flow BC policy + Q-maximizing one-step policy distillationoffline-to-online locomotion/action prior로 가장 실용적
QAM / Q-learning with Adjoint Matching논문critic action-gradient를 adjoint matching objective로 바꿔 flow/diffusion policy를 안정적으로 최적화연속 제어 고성능 후보이나 구현 난이도 높음
Discrete-action Flow Matching Offline RL논문continuous flow 대신 CTMC 기반 Q-weighted flow matching, factorized multi-agent pathSMAC/이산 MARL에 가깝고, 연속 사족보행은 action quantization 필요
TRFP논문one-step sampling을 목표로 한 truncated rectified flow policy실시간 제어 latency 관점에서 유망
BFQ논문short-range displacement를 bootstrapping해 single-step noise-to-action mapping 학습빠른 offline RL 후보. 공개 코드 확인 전에는 FQL 이후 검토
SafeFQL논문reachability-style safety value + one-step flow policy + conformal calibration실로봇 안전/constraint가 중요하면 FQL보다 직접적인 안전 후보

구현 우선순위

MQE: 1순위 SrSv(MAT 자리 교체), 2순위 MAGPO guider, 3순위 SMPE belief, 4순위 DMCG message passing. S2Q/AIR는 MQE가 연속 행동 PPO/OpenRL 중심이라 바로 붙이지 말고 PyMARL 이산 benchmark에서 먼저 검증한다.

사족보행 parkour: 1순위 SMPE/RMA estimator 강화, 2순위 CASH-style capability conditioning, 3순위 SRMT memory, 4순위 FQL/flow matching offline action prior. MAGPO/SrSv는 여러 로봇 협력 parkour로 확장할 때만 본격 투입한다.

🔗 융합 분석 — marl_hub 기술을 어떻게 도입·융합할까

두 외부 사족보행 환경의 저장소를 실제로 clone·코드 분석해, marl_hub의 19개 기술 중 가장 잘 붙는 5개씩을 골랐다. 각 카드는 🔍쉽게 / 🧩무엇을 도입 / 🔧어떻게 융합(단계) / ✅기대 효과로 정리. 적합도 색: 🟰 거의 그대로 · 🟢 높음(포팅 필요) · 🟡 중(부분 이식) · 🟠 확장해야 의미.

🅐 MQE — Multi-Agent Quadruped Environment

이 환경이 뭔가: 여러 마리 Unitree Go1이 협력/경쟁하는 멀티에이전트 환경(문 통과·박스 밀기·양몰이·축구·스모). 코드 확인: Isaac Gym+legged_gym · PyTorch · RL백엔드 OpenRL(이미 ppo/jrpo/mat/dppo 제공) · 에이전트 2~4 · per-agent 보상. 핵심 구조: 상위 정책은 로봇에게 '어디로 가라'는 3차원 속도명령만 출력하고(go1_gate_wrapper.py:13-14), 실제 다리 움직임은 미리 학습된 걷기 정책(walk-these-ways)이 대신 처리(go1.py:389-409). 즉 우리가 바꿀 부분은 '상위 명령 정책'뿐이고 이건 통째로 교체 가능 → 새 MARL 기법 붙이기 매우 쉬움.
🔗 https://ziyanx02.github.io/multiagent-quadruped-environment/

① SrSv — 순차적 의사결정 트랜스포머 (AAAI25) 🟰 최상 (거의 그대로)

🔍 쉽게 말하면 에이전트들이 한 명씩 차례로 행동을 정하는 트랜스포머. 앞 로봇의 결정을 보고 다음 로봇이 정해 '팀 호흡'이 맞는다. SrSv는 거기에 미래 보상 예측(가치)도 순차로 계산해 안정성을 높였다.

🧩 무엇을 도입 SrSv의 autoregressive 트랜스포머 actor + 순차 가치 critic 통째로.

🔧 어떻게 융합 MQE는 이미 같은 계열인 MAT를 --algo mat로 돌린다(cfgs/mat.yaml). ① SrSv 네트워크를 OpenRL의 MAT 자리에 등록 → ② cfgs/srsv.yaml 만들어 연속(Gaussian) 행동 헤드로 설정 → ③ 관측이 이미 (envs, agents, dim) 형태라 그대로 입력. 거의 코드 수정 없이 교체.

✅ 기대 효과 문 통과·박스 밀기처럼 순서가 중요한 협력(누가 먼저 들어가고 누가 받칠지)에서 팀 조율·성공률↑.

② MAGPO — 학습용 '코치'가 탐험을 이끄는 PPO (ICLR26) 🟢 높음

🔍 쉽게 말하면 학습할 때만 전체 상황을 다 보는 코치(guider)가 좋은 행동을 시범 보이고, 실제 실행은 각 로봇이 자기 시야만으로 한다. 코치가 탐험을 이끌어 어려운 협력을 빨리 배운다.

🧩 무엇을 도입 중앙집중 guider 정책 + 분산 정책이 코치를 따라가게 하는 정렬 손실.

🔧 어떻게 융합 ① OpenRL PPO 루프에 guider 네트워크 추가(전체 에이전트 관측을 한꺼번에 입력) → ② 각 로봇 정책 손실에 'guider 따라가기' 항 추가 → ③ MQE의 per-agent 보상을 공유 advantage로 사용. 비용: MAGPO가 JAX(Mava)라 PyTorch/OpenRL로 알고리즘 포팅 필요(구조는 동일).

✅ 기대 효과 양몰이-hard처럼 탐험이 어려운 과제에서 수렴 속도·성공률↑.

③ CASH — 로봇 '능력 카드'로 역할을 나누는 정책 (CoRL25) 🟢 높음

🔍 쉽게 말하면 각 로봇에게 '능력 카드'(속도·역할 등)를 같이 입력하면, 하나의 정책이 능력에 맞춰 다르게 행동한다. 공격수/수비수 분담이나 새 팀 구성에도 바로 적응.

🧩 무엇을 도입 능력 벡터를 받아 정책 가중치를 즉석 생성하는 하이퍼네트워크 디코더(MAPPO에 붙는 플러그인).

🔧 어떻게 융합 ① MQE 관측에 각 Go1의 역할/능력 벡터(예: 공격수=1, 최대속도) 추가 → ② 상위 정책 앞에 CASH 하이퍼네트 삽입(capability_aware=on) → ③ football-2vs2·스모처럼 역할이 갈리는 과제에 적용. 비용: JaxMARL→PyTorch 포팅.

✅ 기대 효과 한 정책으로 공격/수비 자동 분담, 빠른 개·느린 개 섞인 팀에도 일반화.

④ SMPE — 안 보이는 상황을 '상상'해 보완 (ICML25) 🟡 중상

🔍 쉽게 말하면 각 로봇이 자기가 못 보는 부분(다른 로봇·공의 전체 위치)을 머릿속으로 상상(복원)해 판단에 쓴다. 부분관측의 약점을 메운다.

🧩 무엇을 도입 비관측 상태를 추정하는 per-agent VAE belief 모듈(정책과 분리된 표현학습기).

🔧 어떻게 융합 ① MQE 각 로봇 관측을 VAE 인코더에 통과 → belief z 생성 → ② z를 상위 정책 입력에 이어붙임 → ③ VAE는 재구성 손실로 따로 학습(정책과 분리). 비용: SMPE 원구현이 이산 행동이라 정책 헤드를 MQE 연속(3차원)으로 교체.

✅ 기대 효과 시야 밖 협력(박스 밀기에서 안 보이는 파트너 위치 추정)이 정확해져 협력 품질↑.

⑤ DMCG — '누가 누구와 협력' 관계 그래프 (arXiv25) 🟡 중 (아이디어만 이식)

🔍 쉽게 말하면 로봇들을 그래프 노드로 보고 '누가 누구와 협력할지' 메시지를 주고받아 공동 행동을 정한다.

🧩 무엇을 도입 에이전트 간 관계를 모델링하는 그래프 메시지패싱 모듈(공동 행동 조율).

🔧 어떻게 융합 ① 로봇들을 노드로 그래프 구성 → ② 메시지패싱으로 이웃의 의도 교환 → ③ 결과를 상위 정책 특징에 추가. 비용: DMCG는 가치기반(Q러닝)이라 코드 통째 이식은 안 되고, 메시지패싱 '구조'만 떼어 PPO actor에 붙임.

✅ 기대 효과 다수 협력(양몰이)에서 역할 분담·충돌 회피↑.

왜 나머지는 안 맞나(정직): VIKI-R·MARTI·PettingLLMs는 LLM(언어모델)용이라 로봇 제어와 무관 · verl·AReaL·siiRL은 LLM 학습 인프라 · S2Q·AIR·ComaDICE는 이산 행동·오프라인이라 MQE의 연속·실시간과 안 맞음 · ACAC는 비동기·이산 매크로행동이라 MQE의 동기·연속과 불일치.

🅑 Isaaclab_Parkour (CAI23sbP)

이 환경이 뭔가: 한 대의 Unitree Go2가 장애물 지형(틈·허들·계단)을 넘는 parkour 학습. 코드 확인: Isaac Lab(Isaac Sim 4.5) · PyTorch · rsl_rl 커스텀 · teacher-student 증류(특권정보 가진 teacher → 카메라만 쓰는 student로 전수) + RMA 방식으로 안 보이는 물리값(질량·마찰)을 과거 데이터로 추정(parkour_rl_cfg.py:44-49) · 관측 prop53+지형스캔132+priv_latent29(질량/COM/마찰) · student는 depth카메라+GRU기억. ⚠️ 멀티에이전트가 아님 → 융합은 ① 기존 단일로봇 파이프라인에 아이디어 이식, 또는 ② 여러 마리로 확장(MARL 레이어 신설 필요) 둘 중 하나.
🔗 https://github.com/CAI23sbP/Isaaclab_Parkour

① SMPE — 안 보이는 물리값 추정을 더 정교하게 (ICML25) 🟰 최상 (이미 같은 일을 함)

🔍 쉽게 말하면 Parkour는 이미 로봇이 못 느끼는 물리값(질량·마찰)을 과거 데이터로 추정한다(RMA estimator). SMPE의 VAE는 같은 일을 더 정교하게(belief 복원 + 불확실성 표현)한다 — 발상이 완전히 동일.

🧩 무엇을 도입 SMPE의 VAE belief + Filter 가중 복원 모듈.

🔧 어떻게 융합 ① Parkour의 상태추정기 DefaultEstimator를 SMPE VAE 인코더로 교체 → ② priv_latent(질량/COM/마찰) 추정을 VAE 재구성으로 학습 → ③ (옵션) SMPE의 탐험 보너스를 지형 커리큘럼에 추가. 둘 다 PyTorch라 포팅 쉬움.

✅ 기대 효과 물리값이 바뀌어도(도메인 무작위화·sim2real) 더 강건, 어려운 지형 탐험↑.

② CASH — 무작위화한 물리값을 정책에 직접 알려주기 (CoRL25) 🟢 중상

🔍 쉽게 말하면 Parkour는 학습 때 로봇 물리값을 무작위로 바꾼다(priv_latent). CASH는 그 물리값을 '능력 카드'로 정책에 직접 입력해, 물리가 변해도 거기 맞춰 행동하게 만든다.

🧩 무엇을 도입 물리값(priv_latent)을 받아 정책 가중치를 생성하는 하이퍼네트.

🔧 어떻게 융합 ① priv_latent 29차원을 CASH 하이퍼네트의 능력 입력으로 연결 → ② actor 가중치를 물리값에 따라 생성 → ③ teacher(특권 접근)에 먼저 적용 후 student로 증류. 비용: JAX→PyTorch. 보너스: 여러 종류 로봇으로 확장하면 그대로 이질 다로봇 지원.

✅ 기대 효과 질량·마찰 변화와 sim2real 갭에 강건한 단일 정책.

③ SRMT — 카메라 기억을 GRU 대신 트랜스포머로 (arXiv25) 🟡 중

🔍 쉽게 말하면 Parkour student는 카메라(depth)만 보고 걸으며 과거를 GRU로 기억한다. SRMT는 그 기억을 트랜스포머 attention으로 바꿔 더 길게·선택적으로 기억한다.

🧩 무엇을 도입 SRMT의 TransformerCore(GPT2Block) 메모리 모듈.

🔧 어떻게 융합 ① student의 RecurrentDepthBackbone(GRU)를 SRMT attention 메모리 코어로 교체(SRMT가 RNN↔attn 토글 설계라 교체 쉬움) → ② depth 특징 시퀀스를 attention으로 집약 → ③ 멀티에이전트 공유메모리 부분은 빼고 단일 로봇용으로.

✅ 기대 효과 잠깐 가려지거나 사라지는 장애물에서 기억 기반 판단↑.

④ MAGPO — 여러 마리 협력 parkour로 확장 (ICLR26) 🟠 확장해야 의미 있음

🔍 쉽게 말하면 여러 마리 Go2가 함께 parkour 하게 만들고 싶을 때, '코치가 조율하는' MARL로 좁은 통로·다리를 팀으로 통과.

🧩 무엇을 도입 CTDE guider+분산 PPO 알고리즘.

🔧 어떻게 융합 ① 먼저 Isaac Lab 씬에 로봇 여러 대 추가(현재 1대 → InteractiveScene에 N대) + 멀티에이전트 환경 래퍼 신설 → ② 그 위에 MAGPO 적용. 비용: 지금은 MARL 구조가 아예 없어 새로 만들어야 함 + JAX 포팅. 큰 작업.

✅ 기대 효과 좁은 다리·통로 등 협력 통과 가능.

⑤ DMCG — 여러 마리 순서 조율 그래프 (arXiv25) 🟠 확장해야 의미 있음

🔍 쉽게 말하면 여러 Go2가 지형을 함께 넘을 때 누가 먼저/뒤로 갈지를 그래프로 조율.

🧩 무엇을 도입 에이전트 관계 그래프 메시지패싱.

🔧 어떻게 융합 다로봇 레이어 신설 + DMCG 가치기반을 Isaac Lab PPO로 재구현. 비용: 투자 최대.

✅ 기대 효과 군집(swarm) parkour.
